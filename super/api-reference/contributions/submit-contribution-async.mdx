- The whole request is validated **before** we respond (payload, employer onboarding, every employee, MVR payment gate, active USIs). If anything is wrong you get a `400` listing **every** error and nothing is stored.
- A valid request returns `202 Accepted` with a `transactionId` straight away. The submission to the clearing house happens in the background as **one** transaction (one direct debit).
- The outcome arrives via the `contribution.submission_completed` webhook, or poll `GET /v2/contributions/:transactionId`.

### Idempotency-Key (required)

Send a unique `Idempotency-Key` header with every new submission and **reuse it when retrying the same submission** (e.g. after a timeout or network error).

| Situation | Result |
|---|---|
| Same key + same body | `202` with the original `transactionId` (and its current status) — nothing is submitted twice |
| Same key + different body | `409 Conflict` |
| Header missing | `400` |

Keys are scoped to your client and never expire.

### Limits

**100 funds / 1000 members** per request (v1: 8 funds / 40 members).

### Request Parameters

<ParamField query="Idempotency-Key" type="string" required>
  Your unique key for this submission (e.g. a UUID, or your own pay-run ID). Reuse it when retrying the same request; use a new one for a new submission.
</ParamField>

### Request Body

<ParamField body="employerId" type="string" required>
  Employer ID that this contribution belongs to. The employer must be associated with the authenticated client.
</ParamField>

<ParamField body="contributionDetails" type="object" required>
  Simplified contribution details. Only variable data (fund USIs, amounts, pay periods) is required. Employee and employer static data will be automatically retrieved from the database.
</ParamField>

### Responses

| Code | Description |
|---|---|
| `202` | Accepted — the request passed validation and is queued for background submission. Also returned when the same Idempotency-Key and body are resent (with the submission's current status). |
| `400` | Validation failed — nothing was stored. Business-rule errors (employer, employees, MVR gate, USIs, limits) are listed together in `errors`, each with the path of the offending field. Field-format errors (e.g. a missing amount) and a missing Idempotency-Key are reported in `message`, as in v1. |
| `401` | Unauthorized — invalid authentication credentials |
| `403` | The employerId does not belong to your client account |
| `409` | The Idempotency-Key was already used with a different request body |

### Response fields

<ResponseField name="transactionId" type="string">
  The SuperChoice transaction ID for this submission. It is used everywhere afterwards: GET /v2/contributions/:transactionId, payment status endpoints and payment.status_changed webhooks.
</ResponseField>

<ResponseField name="employerId" type="string">
</ResponseField>

<ResponseField name="status" type="string">
  ACCEPTED on a new submission. A replay returns the submission's current status.
</ResponseField>

<ResponseField name="totals" type="object">
  Totals calculated from the request body

  <Expandable title="properties">
    <ResponseField name="funds" type="integer">
      Number of entries in contributionDetails.funds
    </ResponseField>

    <ResponseField name="members" type="integer">
      Total members across all funds
    </ResponseField>

    <ResponseField name="amount" type="string">
      Sum of every fund's amountForFund.value, as a 2-decimal string
    </ResponseField>
  </Expandable>
</ResponseField>

</ResponseField>

</ResponseField>

</ResponseField>
