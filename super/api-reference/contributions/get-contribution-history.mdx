<Tip>
  **Why it's useful:** Use it to get a status update on every contribution you have submitted.
</Tip>

### Payment Statuses

| `status` | `processingLayer` | What it means |
|---|---|---|
| `SUBMITTED` | `PAYMENT_LAYER` | Contribution submitted, awaiting payment initiation |
| `EMPLOYER_PAYMENT` | `PAYMENT_LAYER` | Payment initiated — the clearing house has acknowledged the contribution and the direct debit is underway |
| `DEBIT_CLEARED` | `PAYMENT_LAYER` | Direct debit successful — money has left the employer's account |
| `FUNDS_IN_TRANSIT` | `PAYMENT_LAYER` | Money has cleared source and is being transferred to the fund |
| `AWAITING_FUND_RESPONSE` | `FUND_LAYER` | Money received by the clearing house; awaiting the fund's processing decision |
| `SETTLED` | `FUND_LAYER` | Fund accepted and applied the contribution |
| `SETTLED_WITH_WARNING` | `FUND_LAYER` | Fund accepted with a warning (e.g. minor data issue noted by fund) |
| `REFUNDED` | `FUND_LAYER` | Fund returned the contribution |
| `DEBIT_FAILED` | `PAYMENT_LAYER` | Direct debit failed — money never left the employer's account |
| `FUND_TRANSFER_FAILED` | `PAYMENT_LAYER` | Fund rejected or failed to receive the transfer |
| `CANCELLED` | any | Payment was cancelled |

### When Statuses Update

Status updates are not real-time. The `status` field is updated automatically by background processes as the payment moves through the clearing house. No action is required from your side.

### Day 0 and the 4pm AEDT banking cut-off

The timeline below is counted in **banking days from Day 0**. Day 0 is set when the clearing house submits the debit request to the bank:

- Submitted **before 4pm AEDT** on a banking day → Day 0 = that same day
- Submitted **at or after 4pm AEDT**, or on a weekend/public holiday → Day 0 = next banking day

For example: submitting on a Friday at 5pm means Day 0 falls on the following Monday, since the 4pm cut-off is missed and the weekend is skipped — effectively pushing the entire timeline out by 3 days.

### Summary Timeline

| Banking day | Event | Status |
|---|---|---|
| Day 0 | Contribution submitted | `SUBMITTED` |
| Day 1 | Clearing house acknowledges payment | `EMPLOYER_PAYMENT` |
| Day 2–3 | Direct debit clears | `DEBIT_CLEARED` → `FUNDS_IN_TRANSIT` |
| Day 4 | Clearing house receives funds | `AWAITING_FUND_RESPONSE` |
| Day 3–7 *(from 1 Jul 2026)* | Fund processes | `SETTLED` / `SETTLED_WITH_WARNING` / `REFUNDED` |
| Day 18–25 *(before 1 Jul 2026)* | Fund processes | `SETTLED` / `SETTLED_WITH_WARNING` / `REFUNDED` |

> **Note:** The SuperStream process assumes all submissions succeed. The clearing house does not give us an exact settlement date, so the day range above — and the `SETTLED` / `SETTLED_WITH_WARNING` status itself — is only indicative. It is based on the super fund not rejecting the contribution within 3 business days of receiving it.

### Fund Layer Response Fields

When `processingLayer === 'FUND_LAYER'` and the fund has responded, these fields are populated. They are `null` while the payment is in `AWAITING_FUND_RESPONSE`.

| Field | Type | Description |  |
|---|---|---|---|
| `fundResponseType` | string | `NON_REFUND` · `MEMBER_REFUND` · `EMPLOYER_REFUND` · `MEMBER_CONTRIBUTION_TYPE_REFUND` |  |
| `fundResponseSeverity` | string | `INFORMATION` · `WARNING` · `ERROR` |  |
| `fundResponseDescription` | string | Human-readable reason from the fund |  |
| `fundResponseDetailedDescription` | string \ | null | Detailed error description from the fund (`errorDetailedDescription` from the clearing house). Populated alongside `fundResponseDescription`. |
| `fundResponseReceivedAt` | ISO 8601 | When the fund responded |  |

Show `fundResponseDescription` and `fundResponseDetailedDescription` whenever any of the following are true:

- `status === 'SETTLED_WITH_WARNING'`
- `status === 'REFUNDED'`
- `fundResponseSeverity === 'WARNING'` or `'ERROR'`

### Refund Fields

Populated when `fundResponseType` is `MEMBER_REFUND`, `EMPLOYER_REFUND`, or `MEMBER_CONTRIBUTION_TYPE_REFUND`. All five fields are `null` for `NON_REFUND` responses (i.e. `SETTLED` and `SETTLED_WITH_WARNING`).

| Field | Type | Present when |  |
|---|---|---|---|
| `fundRefundPrn` | string \ | null | `MEMBER_REFUND`, `EMPLOYER_REFUND`, `MEMBER_CONTRIBUTION_TYPE_REFUND` |
| `fundRefundEmployerAmount` | number \ | null | Same as above — amount refunded to employer (AUD) |
| `fundRefundMemberAmount` | number \ | null | `MEMBER_REFUND` only — amount refunded to member (AUD) |
| `fundRefundContributionType` | string \ | null | `MEMBER_CONTRIBUTION_TYPE_REFUND` only — e.g. `SuperannuationContribution.PersonalContributions.Amount` |
| `fundRefundContributionAmount` | number \ | null | `MEMBER_CONTRIBUTION_TYPE_REFUND` only — contribution amount refunded (AUD) |

### Determining Completion

A payment record is fully complete (no further changes expected) when `status` is one of: `SETTLED`, `SETTLED_WITH_WARNING`, `REFUNDED`, `FUND_TRANSFER_FAILED`, `DEBIT_FAILED`, or `CANCELLED`.

### Multi-fund submissions

One submission can include contributions to multiple funds. All records for a submission share the same `transactionId`. A submission is fully complete when every payment record for that `transactionId` has a terminal status. Use the `transactionId` query parameter on this endpoint to retrieve all records for a submission and check each one.

### Multi-fund members

A member is fully complete when all their payment records have a terminal status. Filter by `employeeId` to retrieve all records across all funds for that member.

Note: `fundResponseReceivedAt` is only populated for members with an explicit fund response — members settled silently will have `fundResponseReceivedAt === null` even when `status === 'SETTLED'`. Use the status-based check above instead.

### Request Parameters

<ParamField query="transactionId" type="string">
  Filter to a specific clearing house transaction. Returns all payment records for that submission (one per fund).
</ParamField>

<ParamField query="employerId" type="string">
  Filter contributions by employer ID. When provided, returns contributions only for that employer and verifies the employer belongs to your client. When omitted, returns contributions from all employers belonging to your client.
</ParamField>

<ParamField query="employeeId" type="string">
  Filter contributions by employee/member ID.
</ParamField>

<ParamField query="startDate" type="string">
  Created-at lower bound (ISO 8601). Only contributions submitted on or after this date will be returned.
</ParamField>

<ParamField query="endDate" type="string">
  Created-at upper bound (ISO 8601). Only contributions submitted on or before this date will be returned.
</ParamField>

<ParamField query="page" type="integer">
  Page number (default: 1)
</ParamField>

<ParamField query="limit" type="integer">
  Page size (default: 10, max: 100)
</ParamField>

### Responses

| Code | Description |
|---|---|
| `200` | Successfully retrieved contribution history |
| `400` | Bad request - Invalid query parameters or date format. Check that date parameters are in ISO 8601 format and pagination parameters are valid. |
| `401` | Unauthorized - Invalid authentication credentials |
| `500` | Internal server error - An unexpected error occurred. If this persists, contact support with your transaction ID. |
