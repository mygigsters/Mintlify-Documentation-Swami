### When to Call This Endpoint

Call this endpoint after a transaction has reached `AWAITING_FUND_RESPONSE`, `SETTLED`, `SETTLED_WITH_WARNING`, `REFUNDED`, or `FUND_TRANSFER_FAILED` status in the contribution history. The fund response is only available once the fund has processed the payment and returned a result.

### Top-level

| Field | Type | Description |
|---|---|---|
| `identifier.transactionId.value` | string | The transaction ID submitted with the contribution |
| `identifier.timeInUTC` | number | Epoch milliseconds when the transaction was submitted |
| `responseTransaction` | array | One entry per fund per transaction (see below) |

### responseTransaction[] entry

Each entry is for one fund. It contains either `employerResponseDetails` or `memberResponseDetails` (not both — they are mutually exclusive).

| Field | Type | Description |
|---|---|---|
| `transactionFund.fund.usi` | string | USI of the APRA fund |
| `transactionFund.fund.fen` | string | Fund Employer Number (optional) |
| `transactionFund.smsf` | object | SMSF details if fund is an SMSF (otherwise null) |
| `employerResponseDetails` | object | Employer-level response (null if member-level) |
| `memberResponseDetails` | object | Member-level response (null if employer-level) |

### memberResponseDetails.memberRequest key fields

These fields come from the original contribution submission and are echoed back in the response so you can identify which member this entry belongs to.

| Field | Type | Description |
|---|---|---|
| `memberRequest.employmentPayrollNumber` | string | **Primary identifier** — the payroll number you submitted for this employee. Use this to match the response entry back to the correct employee in your system, especially when multiple members share the same USI |
| `memberRequest.memberNumber` | string | Fund-assigned member number |
| `memberRequest.taxFileNumber` | string | Member TFN |
| `memberRequest.name` | object | Member name (`firstName`, `lastName`) |
| `memberRequest.employmentStatus` | string | e.g. `CASUAL`, `FULL_TIME` |
| `memberRequest.payPeriodStartDate` | number | Pay period start (epoch ms) |
| `memberRequest.payPeriodEndDate` | number | Pay period end (epoch ms) |
| `memberRequest.totalMemberContributionAmount` | object | Total contribution amount for this member |
| `memberRequest.superGuaranteeAmount` | object | SG component |
| `memberRequest.salarySacrificedAmount` | object | Salary sacrifice component |
| `memberRequest.personalContributionsAmount` | object | Personal contributions component |

### employerResponse / memberResponse

| Field | Type | Description |
|---|---|---|
| `responseType` | string | See Response Types below |
| `refundData` | object | Present only for refund response types (`EMPLOYER_REFUND`, `MEMBER_REFUND`, `MEMBER_CONTRIBUTION_TYPE_REFUND`). Omitted entirely (not null) for `NON_REFUND` |
| `errorDetails` | object | Present when the fund has a warning or error to report. Omitted entirely (not null) for a clean NON_REFUND with no notes |

### refundData

| Field | When present | Description |
|---|---|---|
| `employerPaymentPRN` | All refund types | Payment Reference Number for the refund |
| `employerRefundPaymentAmount` | All refund types | Amount refunded to employer |
| `memberRefundPaymentAmount` | `MEMBER_REFUND` | Amount refunded for the member |
| `memberRefundContributionType.contributionType` | `MEMBER_CONTRIBUTION_TYPE_REFUND` | The contribution type being refunded |
| `memberRefundContributionType.contributionTypeAmount` | `MEMBER_CONTRIBUTION_TYPE_REFUND` | Amount of that contribution type refunded |

### errorDetails

| Field | Type | Description |
|---|---|---|
| `errorSeverityCode` | string | See Error Severity Codes below |
| `errorDescription` | string | Standard error message |

### Response Types

`responseType` on `employerResponse.responseType` or `memberResponse.responseType`:

| Value | Meaning |
|---|---|
| `NON_REFUND` | Contribution accepted by the fund — no refund issued |
| `EMPLOYER_REFUND` | Entire contribution refunded to employer (e.g. fund rejected it) |
| `MEMBER_REFUND` | Contribution refunded for a specific member |
| `MEMBER_CONTRIBUTION_TYPE_REFUND` | A specific contribution type refunded for a member (e.g. personal contributions amount) |

### Error Severity Codes

`errorSeverityCode` on `errorDetails.errorSeverityCode`:

| Value | Meaning |
|---|---|
| `ERROR` | Hard error — contribution rejected or refunded |
| `WARNING` | Accepted with a warning (e.g. minor data issue noted by fund) |
| `INFORMATION` | Accepted; informational note only |
| `Response` | Standard response acknowledgement |
| `Partial` | Partial acceptance |
| `Progressive` | Progressive/interim status |

### When does a member appear in the response?

Not every member appears in `responseTransaction`. The fund only includes entries when it has something to report:

| Scenario | Appears in response? | `responseType` | `errorDetails` |
|---|---|---|---|
| Contribution accepted, no issues | **No** | — | — |
| Accepted with a warning/note from fund | **Yes** | `NON_REFUND` | Present (`WARNING` or `INFORMATION`) |
| Contribution rejected / refunded | **Yes** | `EMPLOYER_REFUND`, `MEMBER_REFUND`, or `MEMBER_CONTRIBUTION_TYPE_REFUND` | Present (`ERROR`) |

So **absence means clean success**. If a member appears with `NON_REFUND + WARNING`, their contribution was still processed — the fund is just flagging a note (e.g. account number was auto-corrected). If they appear with a refund type, the contribution was rejected and money is being returned.

### When does the payment status update?

After a payment reaches `AWAITING_FUND_RESPONSE`, a background process polls the fund response once the response window has passed. When the fund responds, the payment status in the contribution history will update to one of the following terminal statuses:

| Fund response | Payment status |
|---|---|
| Contribution accepted, no issues | `SETTLED` |
| Contribution accepted with a warning | `SETTLED_WITH_WARNING` |
| Contribution refunded | `REFUNDED` |
| Hard error from fund | `FUND_TRANSFER_FAILED` |

Each status change also triggers a `payment.status_changed` webhook event if a webhook URL is registered.

> **Note:** The SuperStream process assumes all submissions succeed. The clearing house does not give us an exact settlement date, so `SETTLED` / `SETTLED_WITH_WARNING` is only indicative — it is based on the super fund not rejecting the contribution within 3 business days of receiving it.

### Multi-Member USI Note

When multiple members share the same USI and one has an issue, only the member with something to report will appear in `responseTransaction`. A cleanly accepted member will have no entry.

To identify which employee an entry belongs to, read `memberResponseDetails.memberRequest.employmentPayrollNumber`. This is the payroll number you submitted when creating the employee, and it is the only reliable way to match a response entry back to a specific person when multiple members share a USI.

> **Note:** Optional `memberRequest` fields (e.g. `phoneNumber`, `salarySacrificedAmount`, `employmentStartDate`) are only echoed back if they were included in the original contribution submission. Fields not submitted will be absent from the response, not null.

### Responses

| Code | Description |
|---|---|
| `200` | Transaction response retrieved successfully |
| `400` | Bad request - Invalid transaction ID. |
| `401` | Unauthorized - Invalid authentication credentials |
| `404` | Transaction not found |
| `500` | Internal server error. |
