#### Personal Details

| Field | Notes |
|---|---|
| Email | Pre-filled and locked if sent via invite |
| First Name | Required |
| Last Name | Required |
| Gender | Male, Female, Other, Prefer not to say |
| Date of Birth | DD/MM/YYYY — used for ATO lookup in Step 2 |
| Mobile Phone | Australian format (04xx xxx xxx) |
| Address | Google Maps autocomplete — must select from suggestions |
| ABN | 11 digits, formatted as XX XXX XXX XXX |
| Tax File Number (TFN) | 11 digits, masked input |

#### Super Fund Selection

Uses the ATO Stapling API to look up any existing fund — see Section 7 for details.

A) One fund found

Fund is auto-selected. Employee confirms and enters member number (optional).

B) Multiple funds found

Employee is shown all matched funds and must choose one.

C) Fund conflict

Employer pre-loaded a USI but ATO found a different fund. Employee chooses between the two.

D) No fund found

Employee searches manually by fund name, ABN, or USI.

## ATO Super Fund Lookup (Stapling)

What is super stapling?

An ATO requirement from November 2021. When an employee starts a new job and does not choose a fund, the employer must check for an existing ("stapled") fund before opening a default. This prevents accumulation of multiple super accounts.

When the employee completes Step 1, we send the following to the ATO stapling API:

| ATO Response | What the employee sees |
|---|---|
| One fund found | Fund is auto-selected. Employee confirms and continues. |
| Multiple funds found | Employee is shown all matched funds and must choose one. |
| No fund found | Employee searches for their fund manually by name, ABN, or USI. |
| Fund conflicts with employer's pre-loaded USI | Conflict banner shown. Employee chooses between ATO result and employer-provided fund. |

<Note>
  Why this matters: If you are using our Payments API to make contributions, the fund selected here is the one we use to route payments — ensuring contributions go to the correct fund.
</Note>

## Magic Links

When you send an invite from the dashboard (or via bulk upload), the employee or employer receives a unique, single-use link:

```text
https://yourapp.com/super/super-setup?token=abc123&onboardingFor=Talent&clientName=YourCompany
```

1Widget detects the token automatically2Validates the link with our backend3If valid — appropriate onboarding form launches with email pre-filled4If expired or already used — clear error message with option to request a new link

<Note>
  No code needed on your side — as long as `frontendBaseUrl` is set to the URL where the widget is mounted. The `clientName` parameter is used to show the correct support email on error screens.
</Note>

## Integration

How auth works

The widget uses a short-lived JWT for all API calls. Your **backend** exchanges its Basic Auth credentials for a 10-minute JWT, then passes it to the widget at mount time. Basic Auth credentials are **never** sent to the browser.

### Install the package

```bash
npm install github:mygigsters/super-annuation#v2.1.0
```

<Note>
  Always pin to a specific version tag. A QA tag is also available (e.g. `v2.1.0-qa`) for testing against staging.
</Note>

### Store your Basic Auth credential securely

Keep your Basic Auth credential in a secure server-side store — for example AWS Secrets Manager, HashiCorp Vault, KMS, or a backend environment variable. It must never appear in frontend code or any variable that ships to the browser.

```bash
# Example — backend environment variable (or use your preferred secret store)
SUPER_BASIC_AUTH=your-base64-encoded-credential
```

### Create a backend token endpoint

Your backend calls `POST /widget/session` to exchange Basic Auth for a 10-minute JWT, then exposes it to your frontend via an internal route.

```text
POST https://qa-super.mygigsters.com.au/widget/session
Authorization: Basic <base64(apiUsername:apiPassword)>

→ { "token": "eyJhbGci...", "tokenType": "Bearer", "expiresIn": 600 }
```

Expose it to your frontend via an internal endpoint:

```text
GET /api/super-token
→ { "accessToken": "eyJhbGci..." }
```

<Note>
  **Never** call `/widget/session` from the browser. This endpoint only accepts Basic Auth — passing a Bearer token returns 401.
</Note>

### Import the stylesheet

Add this once at your app entry point:

```javascript
import 'super-annuation/style.css'
```

### Mount the widget

<Note>
  Option A — SuperManagementEmbedNo routing needed
</Note>

Fetch the token from your backend at session start, pass it via `config.accessToken`, and provide `onTokenExpired` for automatic renewal.

```javascript
import { useState, useEffect } from 'react'
import { SuperManagementEmbed } from 'super-annuation'
import 'super-annuation/style.css'

export default function SuperPage() {
  const [accessToken, setAccessToken] = useState(null)

  useEffect(() => {
    fetch('/api/super-token')
      .then(r => r.json())
      .then(({ accessToken }) => setAccessToken(accessToken))
  }, [])

  if (!accessToken) return null  // or a loading state

  return (
    <YourSidebarLayout>
      <SuperManagementEmbed
        config={{
          accessToken,
          frontendBaseUrl: `${window.location.origin}/super`,
        }}
        onTokenExpired={async () => {
          const { accessToken } = await fetch('/api/super-token').then(r => r.json())
          return accessToken
        }}
      />
    </YourSidebarLayout>
  )
}
```

<Note>
  Option B — SuperAppRequires React Router v6+
</Note>

Step 1 — Add a catch-all route:

```javascript
import { Routes, Route } from 'react-router-dom'
import SuperRouteWrapper from './SuperRouteWrapper'

<Routes>
  <Route path="/super/*" element={<SuperRouteWrapper />} />
</Routes>
```

Step 2 — Create the wrapper:

```javascript
// SuperRouteWrapper.jsx
import { useState, useEffect } from 'react'
import { SuperApp } from 'super-annuation'
import 'super-annuation/style.css'

const SUPER_PATH = '/super'

export default function SuperRouteWrapper() {
  const [accessToken, setAccessToken] = useState(null)

  useEffect(() => {
    fetch('/api/super-token')
      .then(r => r.json())
      .then(({ accessToken }) => setAccessToken(accessToken))
  }, [])

  if (!accessToken) return null  // or a loading state

  return (
    <YourSidebarLayout>
      <SuperApp
        embedded
        basename={SUPER_PATH}
        config={{
          accessToken,
          frontendBaseUrl: `${window.location.origin}${SUPER_PATH}`,
        }}
        onTokenExpired={async () => {
          const { accessToken } = await fetch('/api/super-token').then(r => r.json())
          return accessToken
        }}
      />
    </YourSidebarLayout>
  )
}
```

Token expiry handling

The widget manages the full token lifecycle automatically. It calls `onTokenExpired` 60 seconds before the token expires — normal sessions never see a 401. **`onTokenExpired` must return the new token string.** If it returns nothing or throws, the widget shows a session-expired error.

If multiple requests expire simultaneously, the widget deduplicates — your `/api/super-token` endpoint is only called once.

## Recommended: Error Boundary

Wrap any super component in an error boundary to prevent unexpected errors from affecting the rest of your application:

```javascript
import { Component } from 'react'
import { SuperManagementEmbed } from 'super-annuation'

class SuperErrorBoundary extends Component {
  state = { hasError: false }
  static getDerivedStateFromError() { return { hasError: true } }
  render() {
    if (this.state.hasError) return <p>Something went wrong. Please refresh.</p>
    return this.props.children
  }
}

export default function SuperPage() {
  return (
    <SuperErrorBoundary>
      <SuperManagementEmbed config={config} />
    </SuperErrorBoundary>
  )
}
```
