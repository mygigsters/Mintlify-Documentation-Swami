---
title: "Receive webhooks"
description: "Get notified about payment, payout, beneficiary, and invoice events as they happen, instead of polling."
---

Webhooks send your server an HTTP `POST` whenever an event you've subscribed to occurs. Use them instead of polling for status.

## Set up a webhook

<Steps>
  <Step title="Open the webhooks page">
    Log in to the portal and go to **Developer Tools > Webhooks**.
  </Step>
  <Step title="Add your endpoint">
    Click **Add Webhook** and enter your webhook URL. It must be served over HTTPS.
  </Step>
  <Step title="Choose events">
    Select the events you want to receive, then save.
  </Step>
  <Step title="Store the signature key">
    A unique signature key is generated for the webhook. You use it to check that incoming requests come from MyGigsters.
  </Step>
</Steps>

## Verify the signature

Every webhook request includes an `x-signature-key` header. Compare it with the signature key configured for your webhook, and reject requests where it doesn't match.

```http Request headers
Content-Type: application/json
x-signature-key: your-generated-signature-key
```

```javascript Node.js
const receivedSignature = req.headers["x-signature-key"];
if (receivedSignature !== process.env.WEBHOOK_SIGNATURE_KEY) {
  return res.status(401).json({ status: "invalid_signature" });
}
```

## Acknowledge the event

Return `200 OK` to confirm you received the event. Respond straight after validating the request and do any long-running work asynchronously.

```javascript Node.js
return res.status(200).json({ status: "received" });
```

## Retries

If your endpoint doesn't return `200 OK`, the delivery counts as failed. MyGigsters retries up to **3 times** before marking the event as failed. A delivery can fail because of:

- a non-200 HTTP status code
- a request timeout
- a network connectivity issue
- an SSL/TLS certificate error
- your endpoint being unavailable

<Note>
  Retries can deliver the same event more than once. Make your handler idempotent so duplicates are safe.
</Note>

## Event structure

Every webhook payload has the same outer envelope. The resource that changed is inside `data`.

| Field | Type | Description |
|---|---|---|
| `code` | string | Unique event identifier, for example `payment_intent.succeeded`. |
| `event_name` | string | Name of the event that triggered the webhook. |
| `type` | string | The category of the event: `payment`, `payout`, `beneficiary`, or `invoice`. |
| `description` | string | Brief description of the event. |
| `data` | object | The resource payload. Its shape depends on the event type. |

<Warning>
  The envelope has no top-level event ID. To match an event to your own records and to detect duplicates:

  - **Payment intents:** use `data.merchant_order_id`, which matches the `job_id` you passed when creating the intent, and `data.id`, the payment intent ID.
  - **Payouts and transfers:** use `data.reference` or `data.remarks`, which carries your internal payout or invoice identifier, and `data.id`.
</Warning>

## Event catalogue

| Event | When it occurs |
|---|---|
| `payment_intent.succeeded` | Occurs when a payment intent has completed execution and funds are secured. |
| `payment_intent.failed` | Occurs when a payment intent has failed to execute or is explicitly cancelled. |
| `refund.succeeded` | Occurs when a payment refund is completed and funds are returned to the payer. |
| `refund.failed` | Occurs when a payment refund request is rejected or declined by the provider. |
| `payment_link.paid` | Occurs when a shopper pays for a payment link successfully. |
| `payment_link.failed` | Occurs when a payment link expires or is unpaid. |
| `payout.succeeded` | Occurs when a worker payout is processed and transferred successfully. |
| `payout.failed` | Occurs when a worker payout fails or gets rejected by the bank. |
| `beneficiary.created` | Occurs when a new worker beneficiary account/bank details profile has been created. |
| `beneficiary.deleted` | Occurs when a worker beneficiary account/bank details profile is deleted. |
| `client.invoice.paid` | Occurs when one or more client invoices have been marked as paid. |

## Best practices

- **Validate signatures.** Check the `x-signature-key` header before processing any webhook data.
- **Respond quickly.** Return `200 OK` as soon as you've validated the request.
- **Handle duplicates.** Use the identifiers described in [Event structure](#event-structure) to avoid processing an event twice.
- **Use HTTPS.** Serve your webhook endpoint over HTTPS.
- **Log webhook activity.** Keep logs of incoming requests and your responses for troubleshooting.

## Manage webhooks

In the portal, under **Developer Tools > Webhooks**, you can create a webhook, update its URL, change its event subscriptions, view the signature key, enable or disable it, and delete it.

You can also manage webhooks through the API:

- `GET /api/v1/webhooks/` lists your registered webhooks and their event subscriptions.
- `POST /api/v1/webhooks/` registers a new webhook URL and event subscriptions.
- `DELETE /api/v1/webhooks/:id` removes a webhook.

## Get help

If you're not receiving webhooks, contact support with:

- the webhook URL
- the event name
- the approximate time of the event
- the response status your endpoint returned
- relevant application logs
