MyGigsters Payments uses conventional HTTP response codes to indicate the success or failure of an API request. In general: codes in the `2xx` range indicate success, codes in the `4xx` range indicate an error caused by the provided information (e.g., missing required fields, invalid BSB, expired token), and codes in the `5xx` range indicate an error with MyGigsters or banking gateway servers.

## Error response format

When an error occurs, the server responds with an HTTP status code and a JSON payload detailing the error code, machine-readable type, and human-friendly explanation.

```json
{
  "status": 400,
  "error_code": "invalid_bsb",
  "message": "BSB must be exactly 6 digits",
  "errors": [
    "BSB must be exactly 6 digits"
  ]
}
```

| Attribute | Type | Description |
|---|---|---|
| `status` | integer | The standard HTTP response code corresponding to the error (e.g. `400`, `401`, `422`). |
| `error_code` | string | A machine-readable snake_case identifier indicating the specific root cause (e.g. `invalid_bsb`, `duplicate_payout`). Programmatic error handling should switch on this field. |
| `message` | string | A human-readable message describing the error with actionable resolution guidance. |
| `errors` | array optional | Optional list of specific field-level validation messages when multiple parameters fail inspection simultaneously. |

## HTTP status codes

| Status | Meaning | Description |
|---|---|---|
| `200 OK` | Success | The request succeeded. Common for successful GET and some PUT/POST requests. |
| `201 Created` | Created | The resource was successfully created. Common for POST requests. |
| `400 Bad Request` | Invalid Request | The request is missing required parameters, contains invalid parameter formats (e.g. non-numeric BSB), or has malformed JSON. |
| `401 Unauthorized` | Auth Failure | No valid credentials provided, expired JWT token, or missing required `X-API-Version: 1.2` header. |
| `402 Payment Required` | Payment / Balance | Insufficient platform wallet balance for payout, card declined, or card expired. |
| `403 Forbidden` | Access Denied | API key lacks permissions/scopes for this action, or account is suspended pending compliance. |
| `404 Not Found` | Resource Missing | The requested resource (e.g. `customer_id` or `intent_id`) does not exist. |
| `409 Conflict` | State Conflict | Duplicate payout reference, duplicate `job_id`, or conflicting idempotency key payload. |
| `422 Unprocessable` | Validation Error | Semantic validation failure, such as an Australian Business Number failing ATO checksum validation or document OCR rejection. |
| `429 Too Many Requests` | Rate Limited | Too many requests sent within a 1-minute window (> 120 req/min). Inspect `Retry-After` header. |
| `500 / 503 Server Error` | Server Failure | Internal server error or upstream banking gateway maintenance. Retry with exponential backoff and an Idempotency-Key. |

## Handling errors

### Retry transient failures

For `5xx` server errors and rate limits (`429`), your application should automatically retry the request. Always use **exponential backoff with jitter** to avoid stampeding the server. For example, wait 1s, then 2s, then 4s, adding a random variance (jitter) to each interval. Check the `Retry-After` HTTP header returned in 429 responses.

### Retry safely with an idempotency key

Whenever retrying state-changing requests (like creating a charge, refund, or payout), always pass the exact same `Idempotency-Key` header. This guarantees that if a network timeout occurs after the payment was processed, retrying the request will return the original saved result without performing a duplicate transaction.

### Switch on the error code

Always inspect the machine-readable `error_code` attribute rather than parsing the human-readable `message` string. Error messages may be clarified or localized over time, while `error_code` values remain strictly backwards-compatible.
